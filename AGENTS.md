# AGENTS.md — `hivemind-telegram-bridge`

Guidance for AI coding agents (and humans) working in this repository. Read it
fully before making changes. It encodes conventions that are not obvious from the
code and that, if ignored, produce work that will be rejected.

## Repo

Bridges a Telegram bot to a HiveMind node: a HiveMind bridge is a satellite
whose input and output are a chat platform instead of a microphone. Inbound
text messages become `recognizer_loop:utterance` bus messages; the hub's
`speak` replies are posted back into the originating Telegram chat. Part of
the [HiveMind](https://github.com/JarbasHiveMind) ecosystem — a protocol for
connecting satellite devices to a hub running
[OpenVoiceOS](https://github.com/OpenVoiceOS). The hub is
[HiveMind-core](https://github.com/JarbasHiveMind/HiveMind-core); the client
library is
[hivemind-bus-client](https://github.com/JarbasHiveMind/hivemind-bus-client).
Sibling bridges with the same shape: `HiveMind_mattermost_bridge` and the
other chat-platform bridges under the org — check them for prior art before
inventing a new pattern here.

## Layout / build / test

- Package module: `hivemind_telegram_bridge/`. Tests live in `tests/` (check
  before adding — do not create a second test directory).
- Set up a throwaway environment inside your clone; never touch a shared venv:
  `python3 -m venv .venv && VIRTUAL_ENV=$PWD/.venv uv pip install -e ".[test]" --prerelease=allow`
- Run the suite in the foreground: `python3 -m pytest tests/ -q`. It mocks
  both the Telegram `Application` and `HiveMessageBusClient`, so it runs
  without a live token or hub — that also means it cannot catch a real
  handshake hang or a real Telegram API break; treat it as a shape/wiring
  check, not a live-behaviour guarantee.
- `uv`, never `pip`. If latest prereleases fail to install or resolve, that is
  a bug to FIX at the source, not to work around with a pin downgrade.

## Tests

- Adversarial by default. A regression test must **fail before the fix and pass
  after** — prove it by reverting only the source (`git apply -R`, never
  `git stash` across worktrees) and watching the test flip.
- Tests must be mutation-proof: gutting the feature must fail the test. A test

## Repo-specific rules

- **Composition, not inheritance.** `HiveMindTelegramBridge` builds (or
  accepts an injected) `HiveMessageBusClient` in `__init__` but does **not**
  connect it there — `HiveMessageBusClient.__init__` never opens a socket.
  The actual connection happens once, in `connect_hivemind()`, called from
  `start()`. Never add a second call to `connect()` or `run_forever()` — the
  client already owns and runs its own reconnect worker thread once
  `connect()` returns.
- **`connect()` must bound `handshake_max_retries`.** The
  `hivemind-bus-client` floor is `>=1.0.13a1`; that client's own default for
  `handshake_max_retries` is `None`, meaning retry forever. A bridge that
  calls `connect()` without an explicit bound hangs indefinitely against a
  stalled or unreachable hub (down, wrong password) instead of failing fast.
  Any change to `connect_hivemind()` must keep — or add, if it is missing —
  an explicit finite `handshake_max_retries`, exposed as a constructor
  parameter so operators can tune it.
- **The hub owns ACL, not this bridge.** A freshly registered HiveMind client
  is denied every message type until an admin runs `hivemind-core allow-msg
  recognizer_loop:utterance <client_id>` (and usually `speak`). This bridge
  has no way to grant itself permissions and must not try to work around a
  denial locally — a silently dropped message on the hub side is the hub
  doing its job, not a bug here. The hub says so with `hive.policy.denied`
  (code `acl_disallowed_type`); the bridge logs the grant hint then, once,
  and never at start (a managed hub grants the type itself).
  `--allowed-chat` is a separate, bridge-side filter over which Telegram chats may originate traffic; it is not a
  substitute for hub-side message-type ACLs.
- **Rejected credentials must fail fast.** A bounded
  `handshake_max_retries` is what turns "wrong access key/password" into a
  clean failure instead of a bridge that spins forever looking connected.
  Do not add retry/backoff logic on top of `connect()` that defeats this.
- **Return upstream responses verbatim.** `handle_speak()` forwards
  `message.data["utterance"]` to Telegram unmodified; do not reformat,
  truncate, or add bridge-specific decoration to hub-authored text. A reply
  longer than one Telegram message is split (`split.py`) in order, never
  shortened: a whitespace run that would make a blank message is joined
  to the text next to it (`_place_whitespace`); only whitespace no message
  could carry beside visible text is left out. The bridge-authored lines are the ones
  in `lines.py`, said only when the hub sent nothing to relay: no skill
  matched (`complete_intent_failure`), or no answer came (reply timeout,
  hub unreachable, refusal). Keep them short and add a language to every
  line at once.
- **Thread safety.** `speak()` runs on the HiveMind bus's own thread, never
  on the asyncio loop Telegram's `Application` uses. Any new HiveMind →
  Telegram path must go through `asyncio.run_coroutine_threadsafe` (or
  `_on_loop`) the same way — a direct `await` from the bus thread will
  raise or silently no-op depending on timing.
- **Neither side waits for the other.** The bus thread never waits for a
  Telegram call (no `future.result()`): it also delivers every other hub
  message and the client's keepalive. The Telegram loop never calls
  `client.emit()`: hub sends go through the single `_hub_sender` thread, in
  order (the client's encrypted transport is not written from two threads).
  `stop()` shuts the hub-send thread down with its queue cancelled.
  Waiting state (`_pending`, one `_Question` per question, matched to
  replies by the `bridge_question` number the hub echoes; typing; the
  per-chat send locks) lives on the
  loop only. `tests/test_latency.py` measures both directions; keep it
  green.
- **Never log what people wrote, nor the token.** `emit()` errors carry the
  serialized message and python-telegram-bot's `InvalidToken` carries the
  token: log the kind of error only, and never chain `InvalidToken`.
